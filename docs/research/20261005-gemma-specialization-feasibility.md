# Gemma를 아가톡에 특화해 더 작게 만들 수 있는가

확인일: **2026-10-05**. 사용자 질문은 필요한 기능만 남겨 용량과 실행 비용을 낮추면서
소리·영상 관찰 품질을 높일 수 있는지다. 이번 결과는 공식 문서·구현과 기존 실측에 대한
연구 검토이며, 새 모델을 학습하거나 제품에 탑재한 결과가 아니다.

## 판단

**기술적으로 가능한 방향이다. 다만 경량화와 영아 관찰 품질 향상은 서로 다른 검증이 필요하다.**
우리 목적에 맞는 데이터로 작은 모델을 학습·증류하면 두 목표를 함께 달성할 가능성이 있다.
반면 완성된 Gemma 파일에서 코딩·수학·외국어 지식만 골라 삭제하는 배포 옵션은 확인하지 못했다.
공개 구성은 언어 decoder, tokenizer/embedding, 음성·시각 encoder와 연결부 등이며,
주제별 지식 파일로 나뉜 구조가 아니다. 상세 구현 근거는 [구성요소 감사](20261005-gemma-component-feasibility.md)를 따른다.

현재 제품 문제에 대한 권장 순서는 **작은 발성 관찰 모델 비교 → 영아 자료로 특화 →
시간순 시각 관찰과 결합 → 필요할 때 문장 생성**이다. Gemma 자체의 구조 변경은 이후 후보로 둔다.
현재 Gemma는 기존 합성 AV 관찰 검사부터 미통과여서, 그 출력을 그대로 정답으로 삼아
작은 모델에 학습시키는 것은 근거가 약하다. 모델을 작게 만드는 것만으로 그 오류가 교정되지 않는다.

## 무엇을 줄이면 무엇이 달라지는가

| 방법 | 줄어들 수 있는 것 | 품질·구현 판단 |
|---|---|---|
| 음성/시각 encoder 제외 | 배포 크기와 해당 경로의 RAM·연산 | 우리에게 필요한 입력 기능을 잃는다. 둘을 모두 쓰는 최종 목표에 그대로 적용하기 어렵다. 사용 시 로딩과 파일에서 제거는 다르다. |
| 추가 양자화 | 가중치 크기, 지원 backend에서 메모리/연산 비용 | 현재 시험 파일은 이미 혼합2/4/8bit QAT다. 더 낮추면 아기 관찰 품질이 좋아진다는 근거는 없다. 재변환·동일 입력 비교가 필요하다. |
| 영상 토큰·문맥·출력 예산 조절 | 주로 실행 RAM과 처리 시간 | 저장된 모델 파일 크기는 대부분 그대로다. 소리 전체와 시간순 coverage를 유지한 채 비교한다. 작은 얼굴/입 움직임 손실과 잘림 여부를 함께 검사한다. |
| LoRA/QLoRA 특화 학습 | 학습 중 필요한 자원 | 영아 관찰이나 한국어 응답 형식이 개선될 가능성이 있지만 기본 모델이 자동으로 작아지지는 않는다. adapter만의 크기를 앱 전체 모델 크기로 쓰지 않는다. [S3] |
| 구조적 가지치기 + 회복 학습 | 층·채널 등 실제 계산 구조와 가중치 | 실제 압축 연구가 있다. Gemma4 E2B의 PLE·AV 연결과 모바일 export까지 검증된 버튼 하나의 작업은 아니다. 일반 text 모델의 논문 압축률을 우리 AV 모델에 적용하지 않는다. [S4–S5] |
| 작은 모델로 증류 | 배포할 student의 가중치·연산 | 목적에 맞는 경량화 경로다. 신뢰할 수 있는 교사/사람의 라벨, 독립 영아 평가가 필요하다. 교사의 잘못된 관찰을 그대로 따라 배우는지 검사한다. |

비구조적으로 일부 가중치를 0으로 만드는 것과 실제 작은 dense 행렬을 만드는 것은 다르다.
0이 많아졌다는 사실만으로 현재 Android 실행기의 용량·지연이 줄었다고 보고하지 않는다.
SliceGPT는 이 차이를 설명하고 더 작은 dense 행렬로 바꾸는 방법을 제시한다. [S4]

## 기존 파일·실측에서 확인한 여지

### 1. 이미 상당히 압축된 모델이다

기존 시험 파일은 **2,588,147,712bytes**이며 카드에 혼합2/4/8bit 모바일 QAT가 명시돼 있다.
공식 카드의 약0.8GB text working footprint와 PLE 약1.12GB memory mapping, encoder의 필요 시 로딩은
2.59GB 전체 AV 파일을 0.8GB로 삭제할 수 있다는 의미가 아니다.
Google의 text-only·PLE 제외 수치도 전체 다운로드 크기와 구분한다.
파일별 값과 고정 revision은 [기존 모델 조사](20261005-compact-model-update.md)에 있다. [S1]

### 2. 출력 문장만 짧게 해서 해결할 지연은 아니다

기존 S25 GPU 20초 합성 입력은 첫 비어 있지 않은 텍스트 콜백까지 **24.17초**,
추론 종료까지 **30.93초**, 연구 runner 전체 **43.29초**였다.
첫 콜백 전 구간에는 입력 처리 등 여러 단계가 섞여 있어 전부 prefill로 단정할 수 없다.
다만 출력 최대 토큰을 줄이는 조치만으로 전체 시간이 충분히 줄어든다고 볼 근거도 없다.
기존 연구 코드에서 `enable_thinking=false`를 이미 전달했으므로 사고 출력을 끄는 것을 새 해결책으로 반복하지 않는다.

이 수치는 실제 앱 MP4 디코딩·화면 표시를 포함한 지연이 아니며 p95도 아니다.
발열3은 연속 시험 뒤 측정됐고 냉각 조건이 통제되지 않았다.
한 번의 20초 분석만으로 발열3이 발생한다고 확정하지 않는다. [L1]

### 3. 시간 흐름을 보존하면서 영상 한 장의 비용을 줄이는 후보가 있다

공식 Gemma4 문서는 이미지당 **70/140/280/560/1120** 토큰 예산을 설명한다.
낮은 예산은 세부 시각 정보와 처리량의 절충이다. 음성은 공식 문서상 초당25토큰이다. [S2]

예를 들어 **연구 입력처럼 20초 음성 + 시간순20장**일 때 문서 기준의 단순 산술은:

- 280토큰/장: 영상5,600 + 음성500 = 매체 약6,100토큰
- 140토큰/장: 영상2,800 + 음성500 = 매체 약3,300토큰

이는 **동일 장수·시간 coverage**를 유지할 때의 토큰 산술이며 실제 LiteRT 토큰 계측·속도 예측이 아니다.
prompt·시각/음성 경계 토큰·출력 여유는 별도다. 이번 구성요소 감사에서 **사용한 Android SDK0.17.1에도
`ExperimentalFlags.visualTokenBudget`→JNI→Gemma4 processor 경로가 있음**을 확인했다.
기존 S25 합성 실행의 capabilities는 `max_vision_token_budget=280`이며 연구 runner에서 이 실험적 값을
별도 지정하지 않았다. 따라서 재학습 없이 확인할 수 있는 구체적 실행 최적화 후보가 생겼다.
다만 고정 artifact의70/140 실행 성공·수치 일치·영아 품질·실제 지연은 아직 측정하지 않았다.
실제 export·runtime 제한과 고정 코드 링크는 구성요소 감사의 범위를 따른다.
Gemma 연구 입력20장과 현재 제품의0.5초 간격40개 시각 관찰도 서로 다른 경로다.

따라서 context8192를 무작정4096으로 줄이거나 중간 소리/장면을 버리는 방식은 권하지 않는다.
가능한 모델 변형에서 관찰 품질을 먼저 통과한 뒤, 같은 시간 coverage의 영상 예산을 한 변수씩 비교한다.

## 품질을 올리는 특화 과제

우선 학습 목표는 다음처럼 직접 관찰하고 검증할 수 있는 항목으로 만든다.

1. **소리와 구간:** 옹알이·웃음·울음/칭얼거림·비아기·모름/겹침, 시작과 끝.
2. **시각 변화:** 얼굴이 보이는 시간, 입 움직임, 웃는 듯한 변화, 가림과 관찰 불가.
3. **시간 관계:** 소리와 시각 변화가 같은 시점인지, 중간에 다른 소리로 바뀌는지.
   얼굴이 보인다는 이유만으로 그 얼굴의 발성이라고 확정하지 않는다.
4. **문장:** 위 관찰에 맞는 자연스러운 한국어 표현. 문장이 유창해져도 발성 검출이
   개선됐다고 세지 않는다. 배고픔·졸림의 원인 라벨은 별도의 상황 근거와 불확실성이 필요하다.

고정된 대사 수만 늘리거나 가짜 욕구 라벨로 학습시키는 것은 이 과제를 해결하지 않는다.
교사 Gemma의 미통과 답변을 자동 정답으로 쓰지 않는다. 공개 자료도 상업 학습/배포 조건을 확인하고,
실제 아기 원본과 파생 미디어·임베딩의 외부 전송 금지를 유지한다.

## 권장 후속 작업과 종료 기준

### A. 작은 발성 모델부터 비교

기존에 확인한 **EfficientAT mn04**는 약4.07MB 학습 파일과 옹알이·아기 웃음·아기 울음 라벨이 있다.
따라서 일반 LLM 전체를 잘라내기 전에 검토할 만하다. **Gemma와 기능이 같거나 아가톡에서 더 정확하다는
뜻은 아니다.** Android 변환·성능·권리 검토가 남아 있다.
LittleBeats의 영아 자료 특화 표현 모델은 비교/교사 후보이며 연령·웃음 라벨·겹침과 권리 제한이 있다. [L2]

- 먼저 고정 pretrained 모델의 같은 원음 성능을 현재 beta26과 비교한다.
- 알려진 약국 영상은 회귀용으로 유지하고 독립 시험셋으로 세지 않는다.
- 후보가 실제 누락/오인 균형을 개선할 때 영아 데이터 특화 또는 작은 student 증류를 검토한다.
- GTCRN 같은 denoiser는 별도 변수로 비교한다. 성인 speech 점수가 좋아도 옹알이·웃음을 지우면 채택하지 않는다.

### B. Gemma 개조는 조건부 후보

공식 구조에 맞는 export 경로를 고정하고, 본래 AV 관찰 실패에 대한 개선 근거를 먼저 확보한다.
그 뒤 한 번에 한 조건을 바꿔 시각 토큰/문맥/실행 비용을 비교한다.
PLE 제거·층/채널 pruning·영아 특화 학습은 각각 다른 후보로 다룬다.
현재 모델을 그대로 재시도하며 우연히 좋은 답이 나올 때까지 반복하지 않는다.

### C. 공통 판정

| 판정 축 | 측정·비교 방법 |
|---|---|
| 아기 발성 누락 | 아기/가족·원본 단위로 학습·검증·시험을 먼저 분리. 잘린 클립/증강 자료를 양쪽에 넣지 않고, 옹알이·웃음·울음별 recall/누락수와 분모를 함께 보고 |
| 잘못된 승인 | 성인 말·TV·무음·음악을 아기로 승인하는 비율, 웃음→울음 등 혼동, 모름/보류율을 함께 보고. 정확도 한 숫자로 숨기지 않음 |
| 시간 흐름 | 동일10/20초의 앞/중간/끝 사건, 웃음→울음/반대 순서, 동시 겹침, 화면 밖 발성·가림을 별도 평가 |
| 잡음 제거 | 같은 원음의 처리 전후를 비교. 볼륨 증가와 실제 인식 회복을 구분하고 발성 손실·새 오인을 집계 |
| 모델의 일반화 | 6–18개월, 서로 다른 가정/전화기/거리/환경을 포함하고 평가자 간 불일치·판정 불가를 남김. 표본 수와 신뢰구간을 보고 |
| 모바일 비용 | 다운로드/설치 용량, 첫 실행/준비 후의 전체 분석 지연, RAM, 냉각 단회/연속 사용의 발열, native 취소 완료를 구분해 측정 |

채택 전 비교 기준과 허용 오인 한계는 결과를 보기 전에 고정한다. 작은 평가셋 통과를 모든
아기/기종의 품질 보장으로 확대하지 않는다. 현 단계에서는 압축률·성능 향상률·필요 학습량을 확정할 수 없다.
